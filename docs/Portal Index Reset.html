⚠ KEEP elastic.options AT ALL COSTS

The single file nothing can rebuild is C:\arcgisportal\index\elastic.options. It is Portal's encrypted bundle of index connection details. It is written once when the index service is created and never again.

Verified on 24 October 2026: Portal does not recreate it when it is missing; Portal Admin's Reconfigure does not; this toolkit cannot; a copy from any other Portal is useless because it is encrypted with this deployment's key; and a byte-level scan of the entire machine, including Portal's Postgres database and WAL, found no second copy anywhere.

Everything else in the index directory can be regenerated: the cluster data by a Full Reindex, the certificates and every yml by RebuildConfig. Lose this one file with no golden copy and the only ways back are a webgisdr restore or Esri Support.

Protect it: run SaveGoldenConfig today, schedule Reset-PortalIndex.cmd SaveGoldenConfig daily, and keep the golden folder off the machine. The same copy also preserves internal_users.yml, needed whenever the cluster is emptied.

What it does

Portal for ArcGIS 12.x keeps its search index in an embedded OpenSearch 2.18 cluster under C:\arcgisportal\index. After a hard reboot or a storage-level DR restore that cluster sometimes refuses to start, and because the Esri-supported rebuild (Reindex / Reconfigure in the Portal Admin API) needs a running index, there is no way back from inside Portal. The toolkit documented here fixes that gap: it moves the damaged cluster aside and leaves an empty index that boots, after which a Full Reindex from the Portal Admin UI repopulates it from the Portal database.

Two files do the work: a PowerShell script holding the logic and a batch file that is the double-click front door for operators. Nothing is ever deleted; every reset moves data into a timestamped backup folder and can be rolled back.

The old 10.x and 11.x approach of unpacking empty_index.zip over the index folder does not exist in 12.x. The config that a bootable index needs is generated per deployment (machine name, cluster name, certificates, Portal's stored index password), so the "template" has to be captured from this deployment while it is healthy. That is what SaveGoldenConfig is for.

The point of the table: everything under nodes\ is derived. The three Portal indices are rebuilt by a Full Reindex (the cluster state's index graveyard shows a Full Reindex already deleted and re-created them once). The security index is re-created from the yml files on first boot because plugins.security.allow_default_init_securityindex is true. The Data Store bookkeeping indices were created by the runtime when the cluster was first built; they were not recreated after the 24 Oct 2026 ResetCluster, and Portal runs without them (five indices instead of eight). An empty nodes\ plus the existing config\ is therefore an empty index that boots.

What the logs showed

  • startup noise — every healthy start logs Not yet initialized (you may need to run securityadmin) three times in the OpenSearch log and SEVERE Error in generating Portal Indices in Portal Index Builder Plugin in the Portal log, then Started Index Service three minutes later. It is a race between Portal and the security plugin, not corruption. Do not treat either message as the fault.
  • 2 Jun 2026 — the whole index service was regenerated: new cluster name, new certificates (visible in openssl.log), dsdata re-initialised. Postgres restarted eight times and the config store reports 12.1.0, so this was almost certainly the 12.1 upgrade. Portal has a code path that builds the index service from nothing, but it runs only during upgrade: on 24 Oct 2026 Portal was started with the index directory absent and created nothing, and Portal Admin's Reconfigure in that state created nothing either.
  • 19 Sep 2026 — seven Portal restarts in one evening. OpenSearch came up every time; Portal's Tomcat was what timed out. No OpenSearch corruption is visible.
  • absent — no node.lock, CorruptIndexException, TranslogCorrupted, bind or certificate errors anywhere in the retained logs. The failing state has not been captured yet. Next time it happens, run Diagnose before touching anything.
  • no backups — the Portal log warns daily that the deployment has never been backed up with webgisdr.

Reset-PortalIndex.cmd recommended front door

Reset-PortalIndex.cmd [Diagnose | SaveGoldenConfig | ResetCluster | ResetClusterGolden | RebuildConfig | RebuildConfigReset | Rollback <backup>]

Double-click it. Windows asks for elevation, then a menu appears: 

  1  Diagnose            read-only health report (always start here)
  2  SaveGoldenConfig    snapshot config + certs while HEALTHY (do this now)
  3  ResetCluster        empty the cluster, keep config/certs
  4  ResetCluster        ...and restore config/certs from the golden copy
  5  RebuildConfig       regenerate certs + config in place (no golden copy needed), keep cluster data
  6  RebuildConfig       ...and empty the cluster as well (config AND data damaged)
  7  Rollback            put a backup back
  Q  Quit

After the chosen action finishes the window pauses so the result can be read, then returns to the menu. Option 7 lists the available backup folders before asking which one to restore.

  • unattended — pass the action as the first argument and the batch file runs it without the menu and exits with the script's exit code: Reset-PortalIndex.cmd Diagnose, Reset-PortalIndex.cmd Rollback 20261025-101500_ResetCluster.
  • overrides — set PORTAL_INSTALLDIR, PORTAL_INDEXDIR or PORTAL_BACKUPROOT in the environment (or edit the top of the file) for a non-default install.
  • execution policy — the script is launched with -ExecutionPolicy Bypass for that one process; machine policy is untouched.
  • output — the console buffer is finite. For Diagnose rely on the report folder it writes rather than scrolling back.
Self-elevation relaunches the file through UAC. A user who cannot answer a UAC prompt should right-click the file and choose Run as administrator instead.

Diagnose read-only

always the first thing to run when the index misbehaves

Checks, in order, and prints a verdict line for each:

  • paths — resolved directories, cluster name, ports, bind names, whether a golden config exists.
  • service & processes — state of the Portal for ArcGIS service and any java.exe whose command line references the index directory or the OpenSearch home. A leftover one holds node.lock and blocks the next start.
  • layout — presence of config, certs, opensearch-security, elastic.options, nodes\0\_state, nodes\0\indices; count of index folders; zero-byte data files (classic hard-reset damage).
  • disk — free space on the index drive.
  • DNS — every host name in network.host and discovery.seed_hosts must resolve, or OpenSearch cannot bind. This is the DR-to-a-renamed-host trap.
  • certificates — each PEM is parsed with openssl (subject, expiry), each key is checked, and the admin_dn in opensearch.yml is shown next to the admin cert CN.
  • cluster — _cluster/health, _cat/indices, _cat/shards with unassigned reasons, security plugin health, and _cluster/allocation/explain when the cluster is red. Cluster state metadata is saved to the report. Yellow is the permanent normal state: every index carries one replica but there is only one node, so the replicas can never be placed. Diagnose says so explicitly and only complains when a primary shard is not started.
  • logs — last 20 lines of the OpenSearch log and out.txt, any JVM crash log, and the last index-related SEVERE/WARNING lines of the newest Portal log. All copied into the report.

Report folder: <BackupRoot>\diagnostics\<timestamp>. Send that folder to Esri Support if it comes to that. Diagnose touches nothing in the index directory and can be run while Portal is up.

openssl verify reports node.pem as self-signed because the node certificate carries the same DN as the CA. That is how Portal generates it and it is not a fault; Diagnose says so in its output.

SaveGoldenConfig read-only on the index

run it today, while the index is healthy; repeat after any RebuildConfig or upgrade

Copies config\ (yml, keystore, certs, security files), elastic.options and the dsdata\etc\*.json files to <BackupRoot>\golden_config, with a README noting when and from which cluster state they were taken. If a golden copy already exists it is renamed with a timestamp rather than overwritten. The action warns and asks for confirmation if OpenSearch is not answering or is red at the time.

This is the 12.x replacement for empty_index.zip. It is specific to this deployment: the config names this machine and cluster, the admin certificate CN is the cluster name, and internal_users.yml must match the password inside elastic.options. It cannot be copied between Portals.

The golden folder contains private keys and the encrypted index credentials. Protect it like a certificate store, and keep a copy off the machine so a DR event does not take it too.

ResetCluster offline

the normal reset: empty cluster, same config, same certificates
  • 1 — copy dsdata\etc\*.json into the backup folder for reference.
  • 2 — stop the Portal for ArcGIS service (up to 10 minutes), then find and, after confirmation, kill any leftover OpenSearch java.exe.
  • 3 — move nodes\ to <BackupRoot>\<timestamp>_ResetCluster\nodes. A move on the same volume is instant regardless of size.
  • 3b — with -FromGolden: also move config\ and elastic.options into the backup and copy the golden versions into place.
  • 4 — start Portal and poll _cluster/health through the admin certificate every 20 seconds for up to -WaitMinutes. Measured: 4 min 33 s.
  • 5 — wait for the security plugin to report UP (it initialises from the yml files a few seconds after the port opens), then print the index list. Expect only .opendistro_security and .plugins-ml-config: Portal does not create ago-items, ago-users and ago-groups at startup, the Full Reindex does.
  • on failure — stop Portal again, keep the failed attempt as nodes_failed_attempt, move the original nodes\ (and config, if replaced) back, start Portal, and exit with an error pointing at the OpenSearch log.

Use plain ResetCluster when Diagnose shows healthy certs and yml but a cluster that will not start or will not go green. Add -FromGolden when Diagnose shows unreadable PEM files, a damaged opensearch.yml or a mangled elastic.options and a golden copy exists. Without one, use RebuildConfig.

RebuildConfig offline no golden copy needed

regenerate certificates and config in place; carry over the two credential files

For a damaged config\ when no golden copy exists. Portal will not do this itself: on 24 Oct 2026 it was started with the index directory absent and created nothing, and Reconfigure in Portal Admin created nothing either. So the script rebuilds the folder from what the install ships and what Portal did at cluster creation.

  • precheck — elastic.options must contain Portal's encrypted credential. opensearch-security\internal_users.yml must contain a bcrypt hash only when the cluster will be emptied (-WithResetCluster) or no security index is found under nodes\; otherwise the live security index already holds the hash and the file is written from the empty template with a warning. Neither file can be regenerated and Portal offers no API to set a new index password, so the action refuses when a needed one is damaged.
  • identity — cluster name, node name and ports are read from the old opensearch.yml if it is still readable, otherwise from dsdata\etc\spatiotemporal-config.json, which lives outside the index directory.
  • 1 — stop Portal and any leftover OpenSearch java.exe; move config\ to the backup folder (and nodes\ too with -WithResetCluster).
  • 2 — generate certs\ with the bundled openssl using Portal's own recipe: RSA 2048, PKCS#8 keys, ten-year validity, CA and node certificate CN *.LOCAL with a critical CA:TRUE constraint on the CA, admin certificate CN equal to the cluster name in upper case. The output matches Portal's originals byte-for-byte in size. The CA key is kept only in the backup folder.
  • 3 — write opensearch.yml from the layout Portal 12.1 generated, with the identity substituted; copy jvm.options, log4j2.properties and opensearch.keystore from the old config when intact, otherwise from Esri's templates; copy the security yml files from the install (they are identical to Portal's); carry over internal_users.yml and leave elastic.options in place.
  • 4 — start Portal and wait for OpenSearch, then for the security plugin and Portal's indices. Rollback of config (and nodes) if it does not come up.

Afterwards run SaveGoldenConfig because the certificates have changed, and a Full Reindex if the cluster was emptied or the Indexer Status counts differ.

The credential pair is the hard floor. Both files are tiny, written once at cluster creation and never touched again, so a crash mid-write cannot hit them; in every break so far they survived. If they are ever lost with no golden copy, the remaining options are webgisdr restore or Esri Support. Scheduling SaveGoldenConfig daily removes that risk.

Rollback

-Action Rollback -BackupName <folder>

Without -BackupName it lists the backup folders and stops. With one, it stops Portal, moves whatever is currently in place into <backup>\replaced_<timestamp>, moves the backed-up nodes and/or config (plus elastic.options when it was saved) back, and starts Portal. Works for ResetCluster and RebuildConfig backups alike. Nothing is discarded in either direction.

Runbook

least destructive first; each rung has an automatic way back
Now, while everything works
  • 1 — copy both scripts to the Portal machine and to the DR/test machine.
  • 2 — run Diagnose on each, read the report, keep it as the healthy baseline.
  • 3 — run SaveGoldenConfig on each; copy the golden folder somewhere off the box.
  • 4 — on the test machine, rehearse ResetCluster followed by a Full Reindex in the UI (see Rehearsing a failure). Done once on 24 Oct 2026; see Verification status.
When the index will not come up
  • 1 — Diagnose. Read the OpenSearch log tail it prints. Fix anything environmental first: a leftover java process, a host name that no longer resolves, a full disk.
  • 2 — ResetCluster, adding -FromGolden (menu option 4) if certs or config looked damaged. This is the expected path: when OpenSearch will not start, Portal Admin's Reconfigure cannot help, because it is driven through the very index service that is down.
  • 3 — certs or config damaged and no golden copy: RebuildConfig (menu 5), or menu 6 if the cluster data is damaged as well.
  • 4 — webgisdr restore, or Esri Support with the Diagnose report folder.
Reconfigure (Portal Admin > System > Indexer) is only an option for the other kind of fault: OpenSearch running and Portal's web tier up, but one Portal index wrong or missing. It needs both to be alive. See Sources.

After any successful reset: Full Reindex from the UI.

Backups live on the same volume as the index so that moves are instant. They are not pruned automatically; once a reset has been proven good and a Full Reindex has completed, the <timestamp>_Reset* folders can be deleted by hand.

After a reset

Portal Admin > System > Indexer > Reindex, mode Full
  • wait — let Portal finish starting. The Portal log shows Started Index Service and then Started web server; the usual Error in generating Portal Indices line in between is expected.
  • check — Portal Admin > System > Indexer > Status. Database counts will be populated, index counts zero: the three ago-* indices do not exist yet.
  • reindex — Reindex with mode Full. This creates ago-items, ago-users and ago-groups and fills them. Search and content listings are unavailable until it finishes. Watch Status until every databaseCount equals its indexCount and syncStatus is true. Judge by these numbers, not by OpenSearch's docs.count, which counts documents rather than Portal items and runs higher.
  • golden — after a RebuildConfig, run SaveGoldenConfig again.

Rehearsing a failure

deterministic ways to break the index on the test machine

Pulling the power on the VM during a Full Reindex is the real cause, but it does not break the index every time. These two recipes imitate a torn write by truncating one file to half its length and fail the same way every time. Keep a pristine copy of nodes first so the test box can be put back without a reindex. 

Stop-Service 'Portal for ArcGIS' -Force
Copy-Item C:\arcgisportal\index\nodes C:\arcgisportal\nodes_pristine -Recurse
Scenario 1: OpenSearch will not start (the DR case, used in the 24 Oct rehearsal)
$state = Get-ChildItem C:\arcgisportal\index\nodes\0\_state -Filter 'segments_*' | Select-Object -First 1
$bytes = [IO.File]::ReadAllBytes($state.FullName)
[IO.File]::WriteAllBytes($state.FullName, $bytes[0..([int]($bytes.Length / 2))])
Start-Service 'Portal for ArcGIS'

Diagnose shows "not listening", the CorruptIndexException cause line, and Portal's failing health check. Recovery: ResetCluster, then Full Reindex.

Scenario 2: OpenSearch starts, one Portal index is red
$seg = Get-ChildItem C:\arcgisportal\index\nodes\0\indices\*\0\index -Filter 'segments_*' |
       Where-Object { $_.FullName -like '*<ago-items uuid from Diagnose>*' } | Select-Object -First 1
$bytes = [IO.File]::ReadAllBytes($seg.FullName)
[IO.File]::WriteAllBytes($seg.FullName, $bytes[0..([int]($bytes.Length / 2))])
Start-Service 'Portal for ArcGIS'

Diagnose shows the cluster red and a warning naming the unstarted primary. This is the case where Portal Admin's Reconfigure is worth trying first; ResetCluster if it does not recover.

Putting the test box back
Stop-Service 'Portal for ArcGIS' -Force
Remove-Item C:\arcgisportal\index\nodes -Recurse -Force
Move-Item C:\arcgisportal\nodes_pristine C:\arcgisportal\index\nodes
Start-Service 'Portal for ArcGIS'

Prevention

cheaper than any reset
  • graceful stop — stop the Portal for ArcGIS service before VM snapshots used for DR, or make sure the hypervisor's shutdown gives Windows time to stop it. OpenSearch survives hard power loss far better than its translog and cluster state do.
  • names — keep the machine name resolvable after a DR restore, or the index cannot bind.
  • webgisdr — schedule it. The deployment has never been backed up.
  • golden config — refresh it after every upgrade or RebuildConfig; store a copy off the box. Schedule Reset-PortalIndex.cmd SaveGoldenConfig daily: it is read-only and takes a second, and it is the only protection for the two credential files nothing can regenerate.

How the script authenticates

admin certificate → PFX in memory → client-certificate TLS to https://localhost:7220

Portal's index password is encrypted in elastic.options and not recoverable. The script does not need it. The security plugin treats any client certificate whose DN is listed in plugins.security.authcz.admin_dn as a super-admin, and Portal generates exactly such a certificate in config\certs\admin.pem with its unencrypted key alongside. The script uses the bundled openssl to wrap the pair into a temporary PFX (3DES/SHA1 so every Windows build can import it), loads it as an X509Certificate2 with a persisted machine key (Schannel cannot present a client certificate whose key is only in memory), deletes the file, and presents it on every REST call. The key container is removed again when the script exits. Server certificate validation is disabled for those calls through a compiled callback, because the node certificate is self-signed and a PowerShell script-block callback fails intermittently on Windows PowerShell 5.1. When the certificate call fails, Diagnose also probes the port without a certificate and reports whether TLS itself or the certificate authentication is at fault, and whether anything is listening on the port.

The same certificate works with securityadmin.bat should a manual re-push of the security configuration ever be needed: 

set OPENSEARCH_JAVA_HOME=C:\ArcGIS\Portal\framework\runtime\jre
cd C:\ArcGIS\Portal\framework\runtime\ds\framework\runtime\opensearch\plugins\opensearch-security\tools
securityadmin.bat -cd C:\arcgisportal\index\config\opensearch-security -icl -nhnv ^
  -cacert C:\arcgisportal\index\config\certs\root-ca.pem ^
  -cert   C:\arcgisportal\index\config\certs\admin.pem ^
  -key    C:\arcgisportal\index\config\certs\admin-key.pem ^
  -h localhost -p 7220
In OpenSearch 2.x securityadmin talks to the REST port (7220 here), not the transport port. The JRE path above is Portal's usual one; the reference copy did not include it, so confirm it exists on the machine.
